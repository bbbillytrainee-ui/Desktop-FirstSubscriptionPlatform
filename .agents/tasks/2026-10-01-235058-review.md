# Production-readiness additions to Mediverse FastAPI backend

This change adds the operational scaffolding needed to run safely on free-tier infrastructure: a daily email-send counter (`EmailSendLog`), the `ResendSender` rate-cap logic, `/health` and `/health/deep` endpoints, slowapi rate limiting on auth routes, structured JSON logging middleware with request ID injection, security headers, Sentry init guard, and CI/deployment config (`ci.yml`, `render.yaml`).

**Watch for:** One confirmed blocking bug — CI tests will always fail because `conftest.py` overwrites `DATABASE_URL` with a hardcoded port-54329 default, bypassing the port-5432 Postgres service that `ci.yml` starts. Render deploys also lack a migration command, so `email_send_log` will not exist in production until migrations are run out of band. `JWT_SECRET` is set with `generateValue: true`, which regenerates on every new Render service deploy and invalidates all active sessions.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The `EmailSendLog` model and migration 0002 are structurally correct — the `down_revision` chains properly to `0f371ba34bfc`, the upsert SQL is idempotent, and the boundary math (count ≤ 90 permits, count 91 blocks) is correct. The migration creates a redundant second unique index on `send_date`, which wastes a small amount of write overhead but does not break anything.

The `ResendSender._check_and_increment` upsert is correct and the `send()` method correctly short-circuits on a `False` return. The test coverage for this path uses mocks rather than a real DB session, so the SQL itself is not exercised by the test suite.

CI has a confirmed broken database connection. `conftest.py` unconditionally overwrites `DATABASE_URL` with `os.environ.get('TEST_DATABASE_URL', 'postgresql+asyncpg://...@localhost:54329/...')`. Because `ci.yml` sets `DATABASE_URL` (port 5432) but never sets `TEST_DATABASE_URL`, every test run in CI connects to port 54329 — where nothing is listening. Migrations run correctly against port 5432 in the "Run migrations" step, but by the time pytest starts, `conftest.py` has redirected the connection elsewhere.

The health endpoints, middleware, Sentry guard, and security headers are all correctly implemented and wired. The middleware execution order (security headers outermost → RequestId → SlowAPI) means all responses, including rate-limit rejections, carry the right headers and request IDs.

`render.yaml` is syntactically valid and sets the right free-tier constraints (1 worker, pool 3+2). It does not include a `preDeployCommand` for `alembic upgrade head`, so `email_send_log` will not exist until migrations are run manually. `JWT_SECRET` uses `generateValue: true`, which rotates on every new service deploy rather than on restart — every deploy forces a full re-login for all users.

## CI database URL mismatch (confirmed blocking)

`conftest.py` runs this at import time:

```python
os.environ["DATABASE_URL"] = os.environ.get(
    "TEST_DATABASE_URL", "postgresql+asyncpg://mediverse@localhost:54329/mediverse_test"
)
```

`ci.yml` sets `DATABASE_URL: postgresql://mediverse:mediverse@localhost:5432/mediverse_test` in the job's `env` block, but it never sets `TEST_DATABASE_URL`. When pytest imports `conftest`, `os.environ.get("TEST_DATABASE_URL", ...)` returns the hardcoded default (port 54329), overwriting the CI env var. The "Run migrations" step earlier in the job ran against port 5432 successfully, but the tests connect to port 54329 where there is no listener.

The fix is one line in `ci.yml`:

```yaml
env:
  DATABASE_URL: postgresql://mediverse:mediverse@localhost:5432/mediverse_test
  TEST_DATABASE_URL: postgresql://mediverse:mediverse@localhost:5432/mediverse_test
```

Alternatively, `conftest.py` can be changed to consult `DATABASE_URL` as a fallback:

```python
os.environ["DATABASE_URL"] = (
    os.environ.get("TEST_DATABASE_URL")
    or os.environ.get("DATABASE_URL")
    or "postgresql+asyncpg://mediverse@localhost:54329/mediverse_test"
)
```

## Missing migration command in render.yaml (confirmed blocking)

`render.yaml` builds with `pip install uv && uv sync --frozen` and starts with `gunicorn ...`. There is no `preDeployCommand`. Render's free web services support `preDeployCommand` for exactly this pattern:

```yaml
preDeployCommand: uv run alembic upgrade head
```

Without it, `email_send_log` does not exist when the application first starts. `ResendSender._check_and_increment` catches `Exception` and returns `True` (fail-open), so the cap is silently disabled rather than crashing — but every email send generates a warning log until the migration is applied manually.

## JWT_SECRET rotation on deploy

`generateValue: true` in Render's service definition generates a random value when the service is first provisioned. It does not rotate on restart. However, if the service is deleted and recreated (e.g., redeploying from a fresh `render.yaml` apply), a new secret is generated. This invalidates every access token and every stored refresh token hash simultaneously. Given that Render free services are occasionally cycled, this is a meaningful operational risk. The recommended approach is to generate the secret once with `openssl rand -base64 48`, paste it as a manual Render secret, and reference it with `sync: false` like the other sensitive keys.

## Duplicate unique index on email_send_log.send_date

`upgrade()` in `0002_add_email_send_log.py` creates:

1. `sa.UniqueConstraint("send_date", name=op.f("uq_email_send_log_send_date"))` — Postgres materialises this as an implicit unique B-tree index named `uq_email_send_log_send_date`.
2. `op.create_index("ix_email_send_log_date", "email_send_log", ["send_date"], unique=True)` — a second, explicit unique B-tree index on the identical column.

Both indexes must be maintained on every write and both are consulted by the planner (it will use only one). The ON CONFLICT clause in `_check_and_increment` targets `(send_date)`, which resolves to the constraint, not the named index — so operationally there is no bug, just wasted write amplification. The `downgrade()` drops `ix_email_send_log_date` by name and then drops the table (which removes the constraint), so rollback is clean.

## Email cap SQL path not covered by integration tests

`test_email_cap.py` verifies the behavioral contract at the mock boundary: a `False` return from `_check_and_increment` suppresses the HTTP call, and `sessionmaker=None` returns `True`. The actual SQL — the `INSERT ... ON CONFLICT DO UPDATE ... RETURNING count` — is never executed against a real database in the test suite. A test that uses the conftest `session` fixture and calls `_check_and_increment` 91 times (or directly queries `email_send_log` after a send) would catch any drift between the SQL and the model. This is a coverage gap, not a current defect, but the upsert query is the only place the rate cap is enforced.
